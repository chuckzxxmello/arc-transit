# Testing CRUD with PostgreSQL and Arc Transit

## What direct SQL can verify

Direct SQL tests database constraints and prepares synthetic test records. It does not execute Spring authorization, Bean Validation, service normalization, eligibility checks, lifecycle transitions, row-lock coordination, or automatic application audit/history recording. A successful INSERT is not proof that all application rules passed.

For application-compliant writes, create and change records through the UI/application services. Use SQL to inspect the resulting committed data. The supplied seed is a limited exception for disposable test data: it mirrors current fleet/driver registration defaults and explicitly inserts matching initial history and synthetic audit records. Its audit action is SQL_TEST_FIXTURE_CREATED, not a claim that a staff member registered the record through the application.

The scripts target the current V24 schema. They are test utilities, not Flyway migrations. No production rules or schema are changed by the test scripts.

## 1. Create a separate database

1. In pgAdmin, connect to the PostgreSQL server used for local development. The repository defaults to localhost port 5433; check your .env because your configuration can differ.
2. Under Databases, choose Create > Database. Name it exactly `arc_transit_crud_test`.
3. Set Owner to the database login configured by POSTGRES_USER in your local .env. Use a PostgreSQL administrator to create the database if the application login cannot create databases. Keep the application login's existing privileges.
4. Open Query Tool on this new database and run:

```sql
SELECT current_database(), current_user, inet_server_addr(), inet_server_port();
```

Confirm the database name before continuing. Do not use your normal `arc_transit` database. The two write scripts reject database names other than `arc_transit_crud_test` or that name followed by an underscore and lowercase letters/digits.

## 2. Start the application against the test database

Open a fresh PowerShell terminal in `C:\projects\arc-transit`. These overrides apply only to that terminal and its child process. Keep your existing .env unchanged. Replace localhost:5433 if your PostgreSQL host/port differs.

```powershell
Set-Location C:\projects\arc-transit
$env:JAVA_HOME = 'C:\Program Files\Java\jdk-21.0.11'
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
$env:SPRING_DATASOURCE_URL = 'jdbc:postgresql://localhost:5433/arc_transit_crud_test'
$env:ARC_SECURITY_ADMIN_USERNAME = 'sqltestadmin'
$env:ARC_SECURITY_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new(
    '', (Read-Host 'Choose a test administrator password' -AsSecureString)).Password
try {
    .\mvnw.cmd spring-boot:run '-Dspring-boot.run.arguments=--server.port=8081 --server.address=127.0.0.1'
} finally {
    Remove-Item Env:SPRING_DATASOURCE_URL -ErrorAction SilentlyContinue
    Remove-Item Env:ARC_SECURITY_ADMIN_USERNAME -ErrorAction SilentlyContinue
    Remove-Item Env:ARC_SECURITY_ADMIN_PASSWORD -ErrorAction SilentlyContinue
}
```

The existing .env supplies the database login/password. Clear any inherited SPRING_DATASOURCE_USERNAME or SPRING_DATASOURCE_PASSWORD override that points to a different login before starting. Choose a test-only password of 8 to 16 characters with uppercase, lowercase, a digit and punctuation, without spaces. Do not reuse a real password.

Flyway creates and migrates the empty database; Hibernate validates it. Do not create application tables manually or copy an old schema. Wait for successful application startup. Check:

```sql
SELECT version, description, success
FROM arc.flyway_schema_history ORDER BY installed_rank;
```

Expect V1 through V24 with success=true for this repository version. Sign in at http://localhost:8081 with sqltestadmin and the password you chose. If startup fails, keep the exact error and resolve it before loading fixtures. Do not reset Flyway history to suppress a failure.

## 3. Insert the starter test data

Open `tests/sql/01_seed_resources.sql` in pgAdmin Query Tool connected to `arc_transit_crud_test`. Execute the whole file, not a selected INSERT. Let the script manage its own BEGIN/COMMIT in a fresh, idle session.

The transaction creates:

| Record | Identifier | Starting state |
| --- | --- | --- |
| Bus 1 | SQLQA-BUS-01 / SQLQA-PLATE-01 | Administrative INACTIVE, availability UNKNOWN, capacity 40 |
| Bus 2 | SQLQA-BUS-02 / SQLQA-PLATE-02 | Administrative INACTIVE, availability UNKNOWN, capacity 45 |
| Driver 1 | SQLQA-DRV-01 / SQLQA-LICENSE-01 | Employment ACTIVE, availability UNKNOWN, professional license expiring in 365 days |
| Driver 2 | SQLQA-DRV-02 / SQLQA-LICENSE-02 | Same starting state as Driver 1 |

Each record gets one initial UNVERIFIED registration history event and one clearly labeled SQL fixture audit. IDs are generated by PostgreSQL and taken from RETURNING; no fixed IDs, sequence resets, or manual foreign-key guesses are used. Timestamps and version=0 are supplied explicitly. Names and identifiers stay within current application bounds.

The fixtures are deliberately not dispatch-ready. UNKNOWN means staff have not reported availability; ACTIVE employment alone does not establish driver availability or qualification for a particular dispatch. Do not change these defaults to force a dropdown selection.

The seed rejects repeated execution, including after a seeded bus is deleted, to avoid overwriting edited data or recreating misleading history. If any statement fails, run `ROLLBACK;` before the next attempt. A failed transaction can still consume sequence numbers; gaps are normal.

## 4. Check database error handling before editing fixtures

Run the entire `tests/sql/02_constraint_probes.sql` in a fresh, idle Query Tool session. It asserts these expected failures:

| Probe | Expected SQLSTATE / rule |
| --- | --- |
| Capacity zero or 600 | 23514 / capacity range trigger, 1-80 |
| Duplicate plate | 23505 / unique plate |
| Lowercase, padded unit identifier | 23514 / normalized identifier |
| Unit identifier of 31 characters | 22001 / VARCHAR(30) |
| Unknown availability value | 23514 / availability CHECK |
| New availability event without an existing fleet parent | 23503 / history parent guard |
| Change existing availability history | 23514 / append-only history |
| Delete audit history | P0001 / append-only audit trigger |

Each expected failure is caught in its own subtransaction and printed as a PASS notice. An unexpected success or different error fails the script. Look in pgAdmin's Messages tab. The file ends with ROLLBACK, so it retains no probe changes. On an unexpected failure, run ROLLBACK manually before proceeding.

The last probe intentionally demonstrates the application/database boundary: PostgreSQL accepts a 51-character driver first name because the historical column allows 80; current application commands allow only 50. The probe rolls this change back. Repeat the 51-character attempt through Driver Management: the UI must cap the input and the service must reject an oversized command. Database acceptance alone cannot establish application compliance.

## 5. Exercise actual CRUD and inspect the results

Use the application for the actions below. After each action, run `tests/sql/03_inspect_crud.sql` and retain its output alongside the observed UI result. The inspection is read-only. Refresh the module to see changes made outside its current view.

1. **Read:** search Fleet Availability for SQLQA-BUS and Driver Management for SQLQA-DRV. Confirm two of each and their defaults. IDs must match SQL results.
2. **Create:** register a third bus and driver through the UI, using new identifiers such as SQLQA-BUS-03 and SQLQA-DRV-03. Confirm one initial history event and genuine application registration audit per record. The inspection includes their master rows; use the extra query below for their audit/history because its history section follows only SQL-seeded identities.
3. **Update:** edit Bus 1 capacity from 40 to 41 and Driver 1's first name to Sample. Save, refresh, and reopen. Confirm persisted values, a newer updated_at/version, and FLEET_UNIT_UPDATED / DRIVER_UPDATED audit actions. Fixture creation audits and earlier history must remain unchanged.
4. **Duplicate rejection:** try creating another bus with SQLQA-PLATE-01 or SQLQA-BUS-01 and another driver with SQLQA-LICENSE-01 or SQLQA-DRV-01. Expect clear conflict feedback and no extra master record or successful create audit. Repeat using an archived identifier: archival does not release its uniqueness.
5. **Availability:** use the module's availability action to report AVAILABLE with a reason and a nonfuture effective time. Set Bus 1 administrative state ACTIVE separately. Confirm current state agrees with the newest history event, previous state remains recorded, and verification remains UNVERIFIED. A staff report is not verified physical truth.
6. **Archive/restore:** as SYSTEM_ADMIN, archive Bus 2. It must disappear from the active grid, appear in Archived Data, and have a nonnull archived_at. Restore it and confirm the reverse plus the corresponding audits. Archive/restore Driver 2 separately. Do not assume fleet deletion rules also apply to drivers.
7. **Permanent bus deletion:** keep Bus 2 free of operational references, archive it, and delete it through Archived Data. Its fleet master row must disappear; its availability history, fixture audit, archive audit and FLEET_UNIT_DELETED audit must remain. Deletion details must retain ID, unit number and plate. This requires V20 or later.
8. **Referenced bus deletion rejection:** use Bus 1 to create a maintenance request or operational report through the UI. Archive Bus 1 and try permanent deletion. Expect a meaningful linked-record reason; its master row and linked records must remain. Restore it when continuing other tests. Do not remove foreign keys or history to force deletion.
9. **Authorization:** create an OPERATIONS_STAFF account through User Administration and repeat privileged actions under that login. Archive/delete and user administration must follow current service permissions. SQL login privileges do not test application roles. Use a fresh application sign-in after role changes.

For newly created UI records, query by the returned ID and entity type, never ID alone:

```sql
-- Substitute the actual ID from the grid/query; IDs need not start at 1.
SELECT * FROM arc.audit_logs
WHERE entity_name = 'FleetUnit' AND entity_id = 123 ORDER BY timestamp, id;
SELECT * FROM arc.vehicle_availability_history
WHERE fleet_unit_id = 123 ORDER BY recorded_at, id;
-- Driver equivalent: entity_name = 'Driver', arc.driver_availability_history, driver_id.
```

## 6. Cover the other modules through application workflows

Do not build these graphs with standalone INSERT/UPDATE/DELETE statements. Their application rules span multiple records and modules. Use SQL only to inspect committed results.

| Module | Required positive and negative checks | SQL evidence tables |
| --- | --- | --- |
| User Administration | Create/reset 8-16 character complex passwords; 7/17 character rejection; duplicate username/email; profile/role edits; stale edit; last active administrator protection; archive blocks login; historical username cannot be reassigned | app_users (omit password_hash from output), user_roles, username_reservations, audit_logs |
| Routes/schedules | Required fields and limits; ordered stops; edit creates a new version; historical trip retains old version/stops; effective dates and schedule bounds; archive/restore permissions | routes, route_stops, route_versions, route_version_stops, route_schedules |
| Dispatch | Eligible unarchived ACTIVE bus with AVAILABLE report; active, available, qualified/nonexpired driver; active route/effective version; matching schedule; valid departure/arrival interval; overlap and maintenance rejection; two concurrent requests for the same resources; permitted lifecycle transitions | dispatch_assignments, dispatch_events, route_versions, route_schedules |
| Maintenance | Existing bus; required fields; REQUESTED -> APPROVED -> IN_PROGRESS -> COMPLETED; invalid transition/cancel rejection; blocking holds; completion returns reported availability to UNKNOWN; reason and history retention | maintenance_records, maintenance_history, fleet_units, vehicle_availability_history |
| Incidents | Required title/severity; nonfuture effective time; valid optional affected-record/report links; valid status transitions; invalid transitions leave state/history unchanged | incidents, incident_events, operational_reports |
| Operational Reports | Existing affected entity; required report/source fields; nonfuture time; verification workflow/evidence; no automatic claim that reported data is physical truth | operational_reports, report_verification_events |
| Exception Queue | Contradiction detection; repeated scan deduplicates open rule/entity; permitted review transitions and bounded notes; no fabricated master state changes | operational_exceptions, audit_logs |
| Dashboard/Archive/Audit | Counts and filters reflect current records; archived/active separation; deletion preserves audit/history; no audit editing/deleting; authorized access only | Module master tables, audit_logs and history tables |
| All forms | Required/blank/null inputs; exact maximum and maximum+1; control characters; invalid dropdown text/cleared required selection; missing/archived records; stale forms; safe error feedback | Before/after master rows, version, timestamps, audit and business history |

Use `docs/INPUT_VALIDATION.md` for the current 50/100/200/500 tiers and shorter schema-bound identifiers. Do not infer a form limit from VARCHAR alone. New passwords have their own 8-16 rule; use the application encoder, not direct SQL password inserts. Keep unrelated modules' IDs separate even when they share the same numeric value.

Do not use SQL to bypass optimistic locking, archive prerequisites, real references, username reservations, or immutable history. A direct SQL state change does not automatically update updated_at/version or create its service audit and business events.

## 7. Run the existing automated business-rule checks

From the repository root:

```powershell
# Just the SQL files supplied with this guide, in an isolated PostgreSQL cluster:
.\scripts\verify-postgres.ps1 -MavenArguments @('test', '-Dtest=SqlCrudFixtureIntegrationTest')

# All current automated checks, production packaging and HTTP login startup:
.\scripts\verify-postgres.ps1 -MavenArguments @('verify') -SmokeTest
```

The script creates a separate loopback PostgreSQL cluster and stops it afterward. It does not run against your normal application database or your manual CRUD database. Never set ARC_TEST_POSTGRES=true against a database containing valuable data. PostgreSQL binaries and JDK 21 must be installed; use the script's PostgresBin/JavaHome parameters if their paths differ.

Existing integration suites cover application authorization, input bounds, committed account editing/archival, fleet deletion/history/audit rollback, route history, report provenance and concurrent dispatch/deletion workflows. The SQL fixture test separately checks forward migrations, default values/provenance, database-name guards, duplicate-seed rollback and every negative SQL probe. Passing these tests does not prove every browser interaction or every possible business scenario.

## Recording results and ending a test session

For each case record: application revision/build, database name/migration, login role, identifiers and returned IDs, exact input, action, expected result, actual UI message, SQL before/after evidence, and pass/fail. For failures retain the exception/SQLSTATE/constraint and matching server log time, without passwords or hashes. Expected failures must leave no partial committed workflow changes; failure/denial audit events may legitimately be recorded separately.

Stop the test application with Ctrl+C and close its terminal when finished. Keep the separate database and logs if needed for investigation. There is no TRUNCATE, CASCADE, trigger-disabling, history cleanup or database-drop instruction in this workflow. Use application archive operations for repeatable cases or create another empty database named arc_transit_crud_test followed by an underscore and a unique lowercase/digit suffix, then repeat startup/migration/seeding against that name.
